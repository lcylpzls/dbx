# dbx 架构决策记录(ADR)

> 每条记录含:状态、背景、决策、影响、备选方案。状态说明:**已接受**(已定)或 **建议**(等待确认,对应 api-design.md 的待决策点)。

> **2026-08-09:D1–D8 已全部确认,均采用推荐项;ADR-007 / ADR-008 同步转为「已接受」。**

## ADR-001:不做完整 ORM,做薄数据访问层

- **状态**:已接受
- **背景**:AI 辅助开发让「写 SQL」成本大幅下降;完整 ORM 的抽象成本(API 幻觉、N+1、调试困难)反而成为主要负担。
- **决策**:dbx 只覆盖连接、事务、扫描、动态条件、日志、错误与迁移,SQL 主体始终由开发者编写。
- **影响**:学习成本低、行为可预测、性能透明;代价是跨数据库的 SQL 差异需要开发者自行处理。
- **备选**:GORM / ent / sqlc;不采用。

## ADR-002:原生 SQL 优先,构造器只覆盖动态部分

- **状态**:已接受
- **背景**:固定查询用原生 SQL 最清晰;动态过滤/排序/分页是字符串拼接与注入的重灾区。
- **决策**:`Raw` 承载固定 SQL,`Select` 只在 WHERE / ORDER BY / LIMIT 层面安全扩展,不生成 SELECT 主体。
- **影响**:SQL 可审查、可粘贴;动态部分获得类型安全与参数化保证。
- **备选**:完整查询构造器(如 squirrel 风格);不采用,避免退化为 ORM。

## ADR-003:基于 database/sql,驱动由子包承载

- **状态**:已接受
- **背景**:核心包保持零第三方依赖,与 logx 的策略一致;驱动选择权应交给使用者。
- **决策**:核心包只依赖标准库 `database/sql` + errx + logx;`dbx/mysql`、`dbx/sqlite`、`dbx/pg` 各自导入驱动并注册方言。
- **影响**:导入哪个子包,就获得哪个数据库能力;核心 API 不泄漏任何第三方类型。
- **备选**:核心包直接内置三个驱动;不采用,增加体积与耦合。

## ADR-004:方言层只处理最小差异

- **状态**:已接受
- **背景**:三数据库的占位符、分页、自增 ID 返回方式不同,但 SQL 主体语法差异不应由库负责。
- **决策**:`Dialect` 接口覆盖占位符、标识符引用、分页、Returning 等少数能力;不做 SQL 方言翻译。
- **影响**:构造器生成的动态片段在三种数据库上行为一致;手写 SQL 按目标方言编写。
- **备选**:完整方言翻译层;不采用,复杂度与维护成本不成比例。

## ADR-005:安全默认

- **状态**:已接受
- **背景**:AI 生成动态 SQL 时天然倾向于字符串拼接,是注入风险的主要来源。
- **决策**:动态 SQL 只经构造器生成;参数一律占位符;标识符白名单校验;分页参数绑定;禁止公共字符串拼接 API。
- **影响**:安全约束变成 API 形态的一部分,而不是文档约定;误用会直接编译失败或返回 `DBX_BAD_ARGUMENT`。
- **备选**:文档约定「不要拼接」;不采用,约束太弱。

## ADR-006:日志与错误接入自家库栈

- **状态**:已接受
- **背景**:webx / logx / errx 已形成统一库栈,dbx 应保持一致。
- **决策**:日志直接使用 logx,错误统一为 errx `DBX_*` 错误码,并提供 `IsNotFound` 等判定助手。
- **影响**:调用方无需适配;测试借助 logx 测试能力完成。
- **备选**:自定日志接口;见 D5,倾向与 webx 保持一致。

## ADR-007:扫描以泛型为主

- **状态**:已接受(对应 D3 的查询形态与扫描入口,2026-08-09 确认)
- **背景**:Go 1.26 泛型成熟,`One[T]` / `List[T]` 比反射式 `Scan(&dest)` 更直观、更安全。
- **决策**:扫描入口统一为 `One[T]` / `List[T]`;底层用反射读取字段元信息并缓存,`RowMapper` 兜底自定义映射。
- **影响**:调用方类型明确,减少 `any` 误用;热路径性能通过缓存保证。
- **备选**:纯反射 `Query(ctx, &dest, ...)`;不采用,类型安全弱。

## ADR-008:内置轻量迁移

- **状态**:已接受(对应 D7,2026-08-09 确认)
- **背景**:schema 变更需要版本化,完整迁移工具(goose / golang-migrate)是额外依赖。
- **决策**:`dbx/migrate` 按文件名顺序执行 SQL,版本表三方言兼容,支持 embed.FS;v0.1 先 up-only。
- **影响**:小项目无需额外工具;复杂迁移场景(回滚、拆分)留到 v0.2 或交给外部工具。
- **备选**:goose / golang-migrate 集成;不采用,保持零第三方。
